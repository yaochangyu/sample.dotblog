# 同一業務 API 同時接受服務呼叫與使用者呼叫規格

Status: implemented（實作票 01–08 已完成；06、07 票第 6 項紅綠順序待主 session 接受替代證據）

日期：2026-10-15  
狀態：通用設計決策已確認（測試縫、使用者 Token 簽發來源、spec 位置由使用者確認）；已實作（見 issues/01–08）；仍待具體 API 設計的項目見下方「待具體 API 設計的項目」。

## Problem Statement

目前的受保護業務 API 只接受服務對服務的呼叫：呼叫服務以 mTLS 綁定憑證的 Token、請求簽章與 nonce 通過驗證。實際上同一個業務操作（例如建立訂單）也會由使用者直接發起。維護者需要讓同一個端點、同一份業務邏輯同時服務兩種呼叫者，但兩種呼叫者的驗證對象不同：服務要證明服務身分與憑證持有，使用者要證明使用者身分。

若只是把兩種 Token 都放行，會出現幾個風險：服務拿高權限去做本該受使用者權限限制的事（混淆代理人）、攻擊者挑較弱的那條驗證路徑、服務與使用者的權限語意混在一起、冪等去重互相覆蓋，以及稽核分不出實際呼叫者類型。

## Solution

同一個業務端點同時接受兩種呼叫者，驗證與授權在入口分開，業務處理共用：

- 服務呼叫維持現有保護：mTLS 綁定 Token、請求簽章、nonce、既有的撤銷與 fail closed 行為。
- 使用者呼叫使用由同一個授權伺服器簽發、audience 與呼叫者類型不同的使用者 Token，通過使用者驗證與使用者權限判斷。
- 兩條驗證路徑各自產出同一種「已驗證呼叫者」，明確標示呼叫者類型、身分與權限；業務處理只依已驗證呼叫者授權，不看它從哪條路徑來。
- 任何一種呼叫者都不能用另一種的驗證或權限通過；使用者那條較弱的驗證不能讓服務呼叫降級。

## User Stories

1. 身為業務 API 維護者，我希望同一個業務端點同時接受服務呼叫與使用者呼叫，以便同一份業務邏輯不必複製成兩個端點。
2. 身為安全營運人員，我希望每個請求都必須標明並通過其呼叫者類型對應的驗證，以便不能用較弱的驗證路徑取代較強的。
3. 身為呼叫服務維護者，我希望服務呼叫仍要求 mTLS 綁定 Token、請求簽章與 nonce，以便新增使用者驗證不降低服務保護。
4. 身為使用者，我希望以自己的使用者 Token 呼叫業務端點，以便只能操作自己被允許的資料。
5. 身為安全營運人員，我希望服務 Token 與使用者 Token 使用不同的 audience，以便一種 Token 不能被另一種呼叫路徑接受。
6. 身為安全營運人員，我希望 Token 內明確標示呼叫者類型，且該類型只能通過對應的驗證，以便服務不能假裝成使用者，使用者也不能假裝成服務。
7. 身為安全營運人員，我希望使用者持有服務 Token 或服務持有使用者 Token 時，一律被拒絕，以便沒有混用的後門。
8. 身為資料擁有者，我希望使用者呼叫只能存取該使用者自己的業務資料範圍，以便使用者不能看到或操作他人資料。
9. 身為資料擁有者，我希望服務呼叫仍只能存取該 Client 被核准的操作與業務資料範圍，以便服務權限不因新增使用者呼叫而擴大。
10. 身為安全營運人員，我希望服務的高權限不會被用來代替使用者的權限限制，以便不發生混淆代理人問題。
11. 身為業務 API 維護者，我希望兩條驗證路徑都產出統一的已驗證呼叫者，以便授權與業務邏輯只依一種輸入判斷。
12. 身為業務 API 維護者，我希望授權規則依呼叫者類型分開撰寫，以便服務與使用者的權限語意互不干擾。
13. 身為業務操作發起者，我希望使用者重試與服務重試都不會造成重複的業務操作，以便兩種呼叫者共用的業務邏輯仍保持冪等。
14. 身為業務系統維護者，我希望冪等去重依呼叫者類型與已驗證身分分開計算，以便使用者與服務互相不會覆蓋或誤判為重複。
15. 身為業務系統維護者，我希望穩定業務識別在同一呼叫者身分範圍內唯一，以便不同呼叫者即使使用相同識別也不互相衝突。
16. 身為稽核人員，我希望紀錄已驗證呼叫者的類型與身分，以便分辨是服務呼叫還是使用者呼叫。
17. 身為稽核人員，我希望使用者請求不會被記成服務，服務請求不會被記成使用者，以便追查不被混淆。
18. 身為稽核人員，我希望驗證失敗的請求，其宣稱的呼叫者類型與身分只標為未驗證，以便不成為偽造的可信紀錄。
19. 身為安全營運人員，我希望使用者 Token 被驗證簽發者、audience 與有效期，以便偽造或過期的使用者 Token 被拒絕。
20. 身為安全營運人員，我希望使用者 Token 被撤銷或使用者被停用後，後續請求在既有撤銷上限內被拒絕，以便失去資格的使用者不能繼續操作。
21. 身為安全營運人員，我希望查證使用者 Token 的服務故障時沿用 fail closed，以便故障不被當成放行。
22. 身為使用者，我希望驗證失敗時得到明確而不洩漏他人資訊的錯誤，以便知道需要重新登入而不被探測。
23. 身為服務維護者，我希望使用者呼叫路徑不要求 mTLS 與請求簽章，但寫入操作仍有防重放與冪等保護，以便使用者端不需要持有憑證又不被重放濫用。
24. 身為業務 API 維護者，我希望寫入類操作能依呼叫者類型各自設定允許的路徑與政策，以便敏感操作可以只開放其中一種呼叫者。
25. 身為安全營運人員，我希望服務身分不能直接代表使用者呼叫，以便代表使用者的委託另行明確設計，而不是用服務身分假裝。
26. 身為測試維護者，我希望以真實的服務與使用者驗證路徑測試同一個端點，以便不用永遠成功的替身證明保護有效。

## Implementation Decisions

### 呼叫者類型與已驗證呼叫者

- 受保護業務 API 的每個請求必須通過其呼叫者類型對應的驗證：服務呼叫走服務驗證，使用者呼叫走使用者驗證。呼叫者類型由已驗證的 Token 決定，不由請求內容自行宣稱。
- 兩種驗證各自完成後，產出統一的已驗證呼叫者，包含呼叫者類型（服務或使用者）、已驗證身分與權限。業務授權與業務邏輯只依已驗證呼叫者，不依驗證來源路徑。
- 請求自行宣稱的呼叫者類型或身分，一律不可信；驗證失敗時只能標為未驗證。
- 兩種驗證不得互相降級：服務呼叫必須維持既有的 mTLS 綁定、請求簽章、防重放與撤銷規則；使用者驗證的存在不得放寬服務路徑，也不得讓服務 Token 走使用者驗證通過。

### 使用者 Token 與授權伺服器

- 使用者 Token 由已選型的同一個授權伺服器簽發，不引入新的授權產品。
- 使用者 Token 與服務 Token 使用不同的 audience，並在 Token 內標明呼叫者類型；業務 API 只接受對應其驗證路徑的 audience 與類型。
- 使用者 Token 的驗證涵蓋簽發者、audience、有效期、呼叫者類型與使用者有效狀態。
- 使用者 Token 不要求綁定用戶端憑證，也不要求請求簽章；此差異是設計決定，不得因此讓服務呼叫跟著放寬。
- 本 lab 以測試使用者帳號代替真實登入流程；互動式登入介面與使用者管理不在本規格內。
- 使用者 Token 的效期、查證快取與撤銷同步沿用既有的上限與 fail closed 原則，具體數值待具體 API 設計，不自行視為已核准。

### 授權

- 授權規則依呼叫者類型分開定義：服務看被核准的操作與業務資料範圍；使用者看其自己的資料範圍與角色。兩者不得共用同一組 scope 或角色而混淆語意。
- 同一業務操作可以針對呼叫者類型設定不同的允許與拒絕；寫入類或敏感操作可以只允許其中一種呼叫者。
- 服務身分不得代替使用者通過使用者授權；使用者 Token 不得轉手給下游冒充服務。代表使用者呼叫的服務（委託或 token exchange）需另行設計，不在本規格內。

### 業務處理共用

- 同一個業務端點與同一份業務邏輯由兩種呼叫者共用，包含既有的冪等與本地提交保證。
- 冪等去重與穩定業務識別依呼叫者類型與已驗證身分分開計算，使用者與服務、不同使用者之間互不覆蓋、互不誤判為重複。
- 使用者寫入請求沒有請求簽章，因此仍需要防重放與冪等保護：沿用既有的 Idempotency Key 與業務唯一性，防重放機制的具體形式待具體 API 設計。

### 稽核

- 追查紀錄包含已驗證呼叫者的類型與身分、操作與結果，並區分服務呼叫與使用者呼叫。
- 驗證失敗的請求，其宣稱的呼叫者類型與身分只標為未驗證，不記成已驗證呼叫者。
- 紀錄不含原始 Token、私鑰或完整敏感 Body；稽核寫入失敗的處理沿用既有 fail closed 原則。

### 故障處理

- 查證服務（服務或使用者 Token 的查證）故障且沒有符合時效的有效快取時，拒絕處理並明確回報服務錯誤，不誤判為憑證或 Token 無效，沿用既有 fail closed 行為。

## Testing Decisions

好的測試只驗證外部可觀察行為：請求是否被接受、錯誤是否明確、資料範圍是否隔離、業務副作用是否只提交一次、稽核是否區分呼叫者類型。不綁定內部類別、函式呼叫順序或儲存實作。

沿用現有的主要整合測試邊界（真實 Kestrel 與 Reqnroll，從呼叫端直連業務 API），新增「使用者呼叫端」作為另一種呼叫者，對同一個建立訂單端點發送請求。不新增測試介面。採真實的服務與使用者驗證路徑，不以永遠成功的替身證明保護有效。

先例：本專案既有的服務呼叫整合測試、撤銷與 fail closed 情境、稽核情境、冪等與防重放情境，可沿用其步驟與結構。

## Out of Scope

- 代表使用者呼叫的委託、token exchange 或服務代表使用者的授權模型。
- 互動式登入介面、使用者註冊與使用者管理。
- 使用者 Token 綁定用戶端憑證，或要求使用者呼叫簽署請求。
- 使用者驗證的外部身分提供者選型（本次採同一個授權伺服器）。
- Gateway 與其信任契約（沿用 server-to-server 規格的 lab 範圍決定）。
- 跨服務或外部系統的 exactly-once 保證。

## Further Notes

本規格是延伸 server-to-server API 保護規格的新功能。既有規格把「代表使用者存取資源、互動式登入」列為 Out of Scope，本規格處理的是使用者直接呼叫、不經服務代表的情境，兩者不衝突，但不改動既有規格。

詞彙沿用本專案 `GLOSSARY.md`：呼叫服務、Client 身分、已驗證呼叫者、業務操作、穩定業務識別、業務資料範圍。新增的「使用者呼叫者」與「呼叫者類型」應在實作時補進詞彙表，並與既有「呼叫服務」「Client 身分」區分。

### 待具體 API 設計的項目

以下刻意未定，不得自行填入預設值並視為已核准：

- 使用者 Token 的效期、查證快取、撤銷同步機制與使用者停用的傳播方式。
- 使用者寫入請求的防重放機制具體形式（沒有請求簽章時如何防重放）。
- 呼叫者類型與 audience 在 Token 內的具體表示方式。
- 各操作允許的呼叫者類型清單與使用者角色模型。
- 使用者業務資料範圍的定義與判斷方式。
- 服務與使用者的冪等識別範圍具體形式。
- 驗證失敗與拒絕情境的具體 HTTP 狀態與回應格式。
