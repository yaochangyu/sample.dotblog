# 02: 使用者 Token 簽發與使用者驗證路徑

**What to build:** 授權伺服器可為測試使用者簽發使用者 Token，該 Token 帶有獨立於服務 Token 的 audience 與呼叫者類型。業務 API 對建立訂單端點接受有效的使用者 Token，通過使用者驗證後產出類型為使用者的已驗證呼叫者，業務操作以該使用者身分提交。偽造、過期或簽發者不符的使用者 Token 被拒絕。使用者路徑不要求 mTLS 綁定與請求簽章，這是設計上的差異，且不得讓服務路徑跟著放寬。本 lab 以測試使用者帳號代替真實登入流程。

**Blocked by:** 01 — 統一的已驗證呼叫者與呼叫者類型。

**Status:** ready-for-agent

- [ ] 授權伺服器為測試使用者簽發使用者 Token，含獨立 audience 與呼叫者類型；使用同一個已選型的授權伺服器，不引入新產品（AC-D01）。
- [ ] 業務 API 對建立訂單接受有效的使用者 Token，已驗證呼叫者類型為使用者，業務操作以該使用者身分提交（AC-D01）。
- [ ] 偽造、過期或簽發者不符的使用者 Token 被拒絕，且無業務副作用（AC-D06）。
- [ ] 使用者驗證涵蓋簽發者、audience、有效期、呼叫者類型與使用者有效狀態。
- [ ] 使用者路徑不要求 mTLS 與請求簽章；服務路徑的保護要求不因此改變。
- [ ] 使用者 Token 的效期、表示方式（audience 與呼叫者類型）為 lab 暫定值並標註「待使用者確認」。
- [ ] 以真實協定與密碼驗證路徑測試，不以永遠成功的替身取代；每個驗收項目至少對應一個 BDD Scenario，先看到失敗再實作。
- [ ] 互動式登入介面與使用者管理不在本票範圍。
