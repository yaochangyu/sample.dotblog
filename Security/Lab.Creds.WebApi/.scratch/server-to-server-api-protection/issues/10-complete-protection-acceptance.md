### 重現說明（內外部服務）

本 lab 的可重現流程以測試環境執行，所有步驟對應到 feature 中的 Scenario。外部部署需另行建立管理介面與憑證配置流程（見「未完成事項」）。

1. Client 登錄：在授權伺服器登錄 client_id 與其 mTLS 用戶端憑證，並核准 scope 白名單。示範 Client 為 orders-client（orders.read、orders.write）、orders-partner-client（同 scope，資料範圍獨立）與 billing-client（非建立訂單的目標 API）。對應情境：各示範 Client 使用獨立的用戶端憑證。
2. 憑證與簽章配置：每個 Client、每個環境各自配置一組 mTLS 用戶端憑證與一組 ECDSA P-256 請求簽章金鑰，兩者分開登錄與退役，不共用私鑰。對應情境：每 Client 每環境獨立配置私鑰。
3. 取得 Token：以 mTLS 用戶端憑證向授權伺服器 POST connect/token（grant_type=client_credentials、client_id），不接受 Client Secret。回應為綁定該憑證的不透明 Access Token，效期 300 秒。對應情境：mTLS 認證成功後核發短效且綁定憑證的 Token。
4. 呼叫業務 API：以同一張 mTLS 憑證連線，送出 Authorization: Bearer、HTTP Message Signatures（Signature-Input、Signature、Content-Digest、Idempotency-Key），呼叫 POST /orders、GET /orders/{orderId}、POST /orders/{orderId}/cancel。對應情境：正常接入流程串接 mTLS 取得 Token、簽章、nonce、重試、資料範圍與業務去重。
5. 重試：以同一 orderReference 與同一 Idempotency-Key，每次嘗試使用新 nonce 重新簽署。已完成時回應 201 並標示 Idempotent-Replayed: true；仍處理中時回應 409（operation_in_progress）。對應情境：合法重試沿用 Idempotency Key 並以新 nonce 重新簽署後通過請求保護。
6. 正常輪替：先登錄新 mTLS 憑證或新簽章金鑰，切換呼叫端，新憑證取得綁定自己的 Token，最後退役舊配置（退役前必須已有替代者，程式強制）。重疊期建議 7 天，lab 不以計時器強制，改以明確的退役操作代替（lab 暫定，見下）。對應情境：正常輪替依登錄新 mTLS 憑證、切換呼叫端、再退役舊憑證的順序進行。
7. 洩漏撤銷：直接撤銷受影響的 Client、Token、mTLS 憑證或簽章金鑰，不等待重疊期結束。各驗證端於 60 秒內拒絕後續請求，含既有連線。量測見 07 單實作紀錄（Token 撤銷約 10 秒，受查證快取上限約束；其餘約 0.01 至 0.03 秒）。對應情境：撤銷<對象>後後續請求在 60 秒內被阻擋。
