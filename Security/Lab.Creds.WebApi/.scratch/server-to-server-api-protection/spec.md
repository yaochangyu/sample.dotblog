## Problem Statement

內部服務與外部合作廠商需要以服務自身身分安全呼叫 API。單純 API Key 或 Client Credentials 無法同時滿足服務權限隔離、憑證撤銷與輪替、呼叫追查、Token 防冒用、業務去重與請求內容簽章等需求。

呼叫端因逾時重試、攻擊者重放請求，或憑證洩漏時，API 必須維持明確的接受判斷與本地業務提交保證，不能以「Token 有效」取代所有檢查。

## Solution

以集中式 OAuth 2.0 Client Credentials 建立服務身分與授權，使用 mTLS 用戶端認證及憑證綁定 Opaque Token，使 Token 無法被單獨冒用。所有業務 API 採 HTTP Message Signatures，由最終 API 驗證原始呼叫端簽章與防重放資訊。

各 Client 的 API／scope 與業務資料範圍分別檢查；有副作用的操作以穩定業務識別及 Idempotency Key 保證本地提交不重複。集中查證及撤銷流程最多 60 秒內阻擋後續使用，無法取得符合時效的驗證結果時拒絕處理。

## User Stories

1. 身為內部服務維護者，我希望服務使用獨立 Client 身分，以便權限與追查紀錄不與其他服務混用。
2. 身為外部合作廠商，我希望使用明確的 server-to-server 接入契約，以便不需要互動式使用者登入也能取得授權。
3. 身為平台管理者，我希望在集中式授權伺服器管理 Client，以便統一核發與撤銷授權。
4. 身為呼叫服務維護者，我希望以 mTLS 取得 Token，以便不另外管理 Client Secret。
5. 身為 API 維護者，我希望 Access Token 綁定呼叫端憑證，以便偷到 Token 的人不能單憑 Token 呼叫 API。
6. 身為呼叫服務維護者，我希望取得短效 Token 並於到期後重新取得，以便不依賴長期 Token。
7. 身為平台管理者，我希望撤銷服務、Token、憑證或簽章金鑰後最多 60 秒內阻擋後續使用，以便限制洩漏影響。
8. 身為 API 維護者，我希望查證服務故障且沒有時效內的有效快取時拒絕處理，以便不破壞撤銷保證。
9. 身為呼叫服務維護者，我希望暫時無法查證時收到明確服務錯誤，以便不把系統故障誤認為憑證已失效。
10. 身為平台管理者，我希望 API Key 不再承擔認證或授權責任，以便不維護第二套可繞過主要保護的認證入口。
11. 身為平台管理者，我希望有需求時才保留獨立訂閱計量 Key，以便將計量與安全授權分開。
12. 身為 API 維護者，我希望可信 Gateway 可以終止 mTLS，以便支援集中式入口而不失去憑證綁定保證。
13. 身為 API 維護者，我希望阻擋偽造 Gateway 身分資訊及繞過入口的請求，以便不信任呼叫端自行宣稱的驗證結果。
14. 身為資料擁有者，我希望每個 Client 只能呼叫核准的 API 與操作，以便落實服務權限隔離。
15. 身為合作廠商，我希望其他廠商即使有相同 scope 也不能操作我的資料，以便維持資料範圍隔離。
16. 身為 API 維護者，我希望所有業務呼叫都具備標準請求簽章，以便驗證原始呼叫者及被簽署內容。
17. 身為 API 維護者，我希望簽章金鑰屬於 Token 識別的同一 Client，以便拒絕混用不同服務的合法憑證。
18. 身為資料擁有者，我希望 API 核對收到的 Body 與已簽署摘要一致，以便內容遭竄改時被拒絕。
19. 身為 API 維護者，我希望目標、必要標頭及授權脈絡受到簽章保護，以便請求不能被改送或替換語意。
20. 身為 API 維護者，我希望跨執行個體阻擋同一 nonce 的併發重放，以便擴充部署不削弱防重放。
21. 身為呼叫服務維護者，我希望重試時使用新 nonce 與簽章、沿用業務識別及 Idempotency Key，以便合法重試不重做業務副作用。
22. 身為業務操作發起者，我希望相同操作及內容的重試提供既有結果或處理狀態，以便逾時不導致重複提交。
23. 身為業務操作發起者，我希望相同識別卻不同內容時明確被拒絕，以便既有操作不被覆寫。
24. 身為業務系統維護者，我希望更換 Idempotency Key 仍不能重做同一業務操作，以便去重不只依賴呼叫端的請求 Key。
25. 身為業務系統維護者，我希望短期去重紀錄過期後仍維持業務唯一性，以便保存期結束不造成重複副作用。
26. 身為業務系統維護者，我希望併發、當機與提交後回應遺失都不造成重複本地提交，以便重試具備可靠的業務語意。
27. 身為服務維護者，我希望 mTLS 與簽章金鑰分開且各環境獨立，以便用途、輪替與撤銷互不混淆。
28. 身為服務維護者，我希望正常輪替允許新舊金鑰短暫重疊，以便完成切換再退役舊金鑰。
29. 身為安全營運人員，我希望洩漏時直接撤銷受影響的身分或金鑰，以便不必等待正常輪替重疊期。
30. 身為稽核人員，我希望紀錄已驗證 Client、金鑰識別、操作與結果，以便追查實際呼叫者。
31. 身為安全營運人員，我希望未驗證身分與已驗證身分明確區分，以便攻擊者不能偽造可信追查紀錄。
32. 身為資料擁有者，我希望追查紀錄不包含原始 Token、私鑰或完整敏感 Body，以便紀錄不成為洩漏來源。
33. 身為下游整合維護者，我希望本地提交保證與跨系統冪等責任清楚分開，以便不誤認為已具備跨系統 exactly-once。
34. 身為安全營運人員，我希望只有已驗證的管理員能登錄 Client 的憑證與請求簽章金鑰，以便任何人都不能自行把憑證加入信任名單。
35. 身為安全營運人員，我希望 Client 先提出登錄申請，經管理員核准後才生效，以便新的憑證或金鑰在核准前不能取得 Token 或通過簽章驗證。
36. 身為安全營運人員，我希望管理員可以拒絕申請，並記錄拒絕結果，以便可疑或不完整的申請不會生效。
37. 身為安全營運人員，我希望只有已驗證的管理員能退役或撤銷憑證與簽章金鑰，以便不被冒用的管理操作癱瘓正常 Client。
38. 身為服務維護者，我希望管理員身分與 Client 身分分開，且管理憑證不能用來呼叫業務 API 或取得業務 Token，以便管理權限不會被當成業務權限使用。
39. 身為呼叫服務維護者，我希望申請時只提交公開憑證或公鑰，私鑰不離開我的環境，以便授權伺服器與管理員都不會接觸私鑰。
40. 身為稽核人員，我希望每次登錄、核准、拒絕、退役、撤銷都紀錄操作的管理員、時間、對象 Client 與憑證／金鑰指紋，以便事後追查是誰改變了信任名單。
41. 身為稽核人員，我希望管理操作的稽核紀錄寫入失敗時，該管理操作不生效，以便信任名單不會在無紀錄下被改變。
42. 身為安全營運人員，我希望不同 Client 的申請互相隔離，以便管理員核准某個 Client 的申請不會影響其他 Client 的憑證或權限。
43. 身為安全營運人員，我希望已核准但尚未生效、已退役與已撤銷的狀態都明確區分，以便只有有效狀態的憑證與金鑰能通過認證。
44. 身為安全營運人員，我希望只有已登錄且驗證通過的 Client 能為自己提出登錄申請，以便任何人都不能替別的 Client 送申請。
45. 身為安全營運人員，我希望申請者必須證明持有所申請憑證或簽章金鑰的私鑰，以便他人不能用拿到的公開憑證或公鑰冒名申請。
46. 身為服務維護者，我希望 Client 用現有已核准的憑證取得身分後，才能申請輪替成新的憑證或金鑰，以便輪替不需要先放寬認證。
47. 身為安全營運人員，我希望每個 Client 的待核准申請數有上限，以便單一 Client 不能灌滿待核准佇列而拖慢管理員審核。
48. 身為管理員，我希望待核准清單裡每一筆申請都帶有已驗證的申請者身分，以便我核准時知道是誰提出、對應哪個 Client。
49. 身為安全營運人員，我希望申請端點的失敗回應明確且不洩漏他人申請內容，以便拒絕結果不成為探測管道。
50. 身為稽核人員，我希望被拒絕的申請嘗試（身分未驗證、證明失敗、超過上限）也留下紀錄並標為未驗證，以便事後追查濫用嘗試。
51. 身為安全營運人員，我希望被撤銷或停用的 Client 不能再提出申請，以便失去信任的身分不能自行換新憑證復活。
52. 身為平台維運人員，我希望部署多個業務 API 執行個體時，同一份簽章只能被其中一個接受，以便攻擊者不能把側錄的請求分送到不同執行個體重放。
53. 身為平台維運人員，我希望請求簽章的 nonce 登錄是原子的，以便併發重放不會因為兩個執行個體同時檢查而都通過。
54. 身為安全營運人員，我希望防重放紀錄遺失（重啟或被清空）後，遺失前建立的簽章不能再被重放，以便維運事件不會變成重放空隙。
55. 身為呼叫服務維護者，我希望防重放紀錄遺失後，被拒絕的請求只要用新的 nonce 與時間重簽就能通過，以便不需要人工介入。
56. 身為安全營運人員，我希望防重放儲存不可用時請求被拒絕並明確回報服務錯誤，以便故障不會變成放行。
57. 身為呼叫服務維護者，我希望多個業務 API 執行個體併發收到同一筆業務操作時只建立一筆訂單，以便重試與負載平衡不會造成重複副作用。
58. 身為平台維運人員，我希望處理中的租約逾期後其他執行個體可以接手，且未逾期前不會被接手，以便執行個體當機不會讓業務操作永遠卡住，也不會被重複執行。
59. 身為平台維運人員，我希望授權伺服器重啟或換執行個體後，信任名單、登錄申請、稽核與已核發的 Token 仍然存在，以便維運操作不會讓信任狀態消失。
60. 身為管理員，我希望兩位管理員同時處理同一筆申請時只有一個決定生效，以便核准與拒絕不會互相覆蓋。
61. 身為安全營運人員，我希望每個 Client 的待核准上限在併發申請下仍然成立，以便不能靠同時送出多筆申請繞過上限。
62. 身為稽核人員，我希望管理操作的變更與稽核同時成立或同時不成立，套用失敗時留下失敗紀錄，以便信任名單與稽核之間不會不一致。
63. 身為平台維運人員，我希望業務 API 透過授權伺服器取得 Client 的信任資料，以便兩個服務分開部署時仍能判斷撤銷與簽章金鑰歸屬。
64. 身為安全營運人員，我希望撤銷 Client、憑證或簽章金鑰後，所有業務 API 執行個體在明確且可驗證的時間內阻擋，以便撤銷時效不因多執行個體而失效。
65. 身為安全營運人員，我希望業務 API 取不到信任資料時拒絕處理而不是沿用過期狀態，以便授權伺服器故障不會變成放行。
66. 身為平台維運人員，我希望授權伺服器與業務 API 各自只能存取自己的資料庫，以便一個服務被入侵時不會直接取得另一個服務的資料。
67. 身為稽核人員，我希望業務提交失敗時已驗證呼叫者的稽核仍然保留並記錄失敗結果，以便事後能追查被拒絕與失敗的嘗試。
68. 身為開發者，我希望整套保證可以在真實的 PostgreSQL、Redis 與兩個執行個體上自動驗證，以便跨執行個體的保證不是只在文件上宣稱。


## Implementation Decisions

### 實作平台與開發規則

- 業務 API 採 ASP.NET Core 10（.NET 10）。
- 實作遵循 [api.template 開發規則](https://github.com/yaochangyu/api.template/blob/main/CLAUDE.md)，並依其導航閱讀必讀文件與工作項指南。
- 開發新 API 端點前，確認全專案採 API First 或 Code First，不得混用；目前尚未選定。
- 此平台決策不等於選定授權伺服器或 Gateway，也不要求這些元件使用相同技術。

### 已確認的選型

| 面向 | 決策 |
|---|---|
| 授權流程 | OAuth 2.0 Client Credentials，集中式授權伺服器 |
| Token 端點的用戶端認證 | mTLS，不新增 Client Secret |
| Access Token | Opaque Token，綁定呼叫端憑證 |
| Token 有效性 | 集中 introspection；允許符合撤銷上限的快取 |
| API Key | 不作認證或授權；有訂閱計量需求時才另外保留 |
| 請求簽章 | HTTP Message Signatures，所有業務 API 呼叫適用 |
| 簽章驗證 | 最終業務 API 驗證原始呼叫端簽章 |
| 金鑰 | mTLS 與請求簽章私鑰分開；每 Client、每環境獨立 |
| 授權檢查 | Client 的 API／scope 白名單，加業務資料範圍檢查 |
| 業務去重 | 穩定業務識別與 Idempotency Key，保證本地提交不重複 |
| 撤銷時效 | 最多 60 秒內阻擋後續使用已撤銷的 Token／憑證／金鑰／服務身分 |
| 查證故障 | 無仍在允許期限內的有效快取且無法查證時，拒絕處理 |

Client Credentials 是取得授權的流程，不是請求簽章方法。mTLS 用戶端認證與憑證綁定 Token 是不同機制，兩者都必須成立。

### 身分與信任邊界

每個呼叫服務使用獨立 Client 身分，不共用認證憑證；不同環境不得共用私鑰。

授權伺服器負責用戶端認證、核發 Token 與管理授權。API 的接受判斷必須涵蓋 Token、Client、憑證及請求簽章金鑰的有效狀態。

允許 mTLS 在可信 Gateway 終止，但必須符合以下條件：

- Gateway 驗證呼叫端憑證，並在可信邊界內完成 Token 與憑證的綁定驗證。
- Gateway 到業務 API 的通道受保護且經過身分驗證。
- Gateway 移除或覆寫外部請求偽造的憑證／身分資訊。
- 業務 API 不得經由其他入口繞過上述驗證。
- 業務 API 不得直接信任公開請求自行提供的憑證標頭。
- 最終業務 API 仍驗證原始呼叫端的請求簽章。

若中介改寫被簽署的目標、標頭或內容，必須定義可驗證的處理方式；不得把改寫後的內容默認為原始呼叫端簽署的內容。

### 認證與授權流程

1. 呼叫服務以 mTLS 向授權伺服器進行 Client Credentials 請求。
2. 授權伺服器驗證 Client 與憑證狀態，依已核准權限核發綁定該憑證的短效 Opaque Token。
3. 呼叫服務經 mTLS 送出 Token 與已簽署的業務請求。
4. 可信驗證邊界查驗 Token 有效性及憑證綁定，最終 API 驗證請求簽章、簽章金鑰歸屬與防重放資訊。
5. 業務 API 檢查目標 API、必要 scope 與可操作的資料範圍。
6. 有副作用的操作通過業務去重判斷後才執行；純查詢不強套業務去重。

Token 到期後重新取得，不以長期 Token 取代生命週期管理。

scope 決定「可做什麼」，業務資料範圍決定「可對哪些資料做」。例如廠商 A 有讀取訂單權限，不代表可以讀取廠商 B 的訂單。不得僅相信 Body 中宣稱的廠商或租戶識別。

### 撤銷與故障處理

撤銷要求涵蓋服務停用、Token 撤銷、mTLS 憑證撤銷及請求簽章金鑰撤銷。

從撤銷操作生效起，到驗證端阻擋後續使用的總延遲，不得超過 60 秒。狀態同步、正向快取與處理延遲都必須納入此上限，不能讓每層各自快取 60 秒。

停用 Client 或輪替憑證，不得被視為既有 Token 已自動失效。已建立的連線也不得因此繞過後續請求的有效狀態判斷。

無法查證且沒有仍符合時效要求的有效快取時，採 fail closed，不執行業務副作用，並明確回報暫時無法驗證的服務錯誤，不假裝成已確認的憑證無效。

此撤銷保證針對後續請求的接受判斷，不代表已提交的業務副作用會被回滾。

### 請求簽章與防重放

採 HTTP Message Signatures，並在實作前制定共同簽章規則，至少涵蓋：

- HTTP 方法與完整目標，包括會影響業務語意的查詢參數。
- 有 Body 時的內容摘要，以及必要的內容型別與標頭。
- 有副作用操作的 Idempotency Key。
- Token 綁定資訊，防止任意替換授權脈絡。
- 簽章時間、接受期限與每次嘗試的新 nonce。

業務 API 必須核對摘要與收到的實際 Body 相符，不能只驗證摘要欄位的簽章。

驗證端必須確認簽章金鑰屬於 Token 所識別的 Client；不得混用不同 Client 各自合法的 Token、憑證與簽章。

nonce 的判斷與登錄必須能防止併發重放，並在所有可接受該請求的執行個體之間維持一致性。僅加入時間戳或 nonce 欄位，不代表已完成防重放。

nonce 保存期必須涵蓋簽章可接受期間與允許的時鐘容差。

合法重試沿用穩定業務識別與 Idempotency Key，但使用新 nonce 重新簽署。已被接受的同一份簽章重送時，應被防重放機制阻擋。

### 業務冪等與本地提交

防重放與業務冪等是兩個不同保證：

- 防重放阻擋同一份合法簽章再次使用。
- 業務冪等阻擋重新簽署、甚至更換請求 Key 後的同一筆業務操作再次產生副作用。

有副作用的 API 必須使用穩定業務識別與 Idempotency Key。識別範圍及內容比對規則由具體 API 定義，避免不同 Client 的識別互相碰撞。

| 情境 | 必要行為 |
|---|---|
| 相同操作識別、相同業務內容，先前已完成 | 不重做副作用，提供既有結果 |
| 相同操作識別、相同內容，仍在處理中 | 不啟動第二次執行，提供處理狀態 |
| 相同業務識別或 Idempotency Key，卻有不同業務內容 | 拒絕，不覆寫既有操作 |
| 更換 Idempotency Key，但仍是相同業務操作 | 仍由穩定業務識別防止重複提交 |
| Idempotency Key 短期紀錄已過期 | 不得因此失去業務唯一性保證 |

業務內容比對不得將每次重試會改變的 nonce、簽章或 Token 視為業務內容變更。

去重狀態與本地業務提交必須一致處理，涵蓋併發、當機及提交後回應遺失的情境。Idempotency Key 保存期至少涵蓋約定的最長重試期；業務唯一性另外維持。

跨服務與外部系統另訂下游冪等協定，本規格不宣稱跨系統 exactly-once。

### 輪替與追查

正常輪替允許新舊憑證或簽章金鑰短暫重疊：先登錄新金鑰、切換呼叫端，再退役舊金鑰。新憑證須重新取得綁定新憑證的 Token，舊 Token 不可搭配新憑證使用。

疑似洩漏時直接撤銷受影響的憑證、金鑰、Token 或 Client，不等待正常輪替的重疊期結束，並維持 60 秒撤銷上限。

追查紀錄包含已驗證的 Client 身分、憑證／簽章金鑰識別、操作、結果及必要關聯識別。不記錄原始 Token、私鑰或完整敏感 Body。

認證失敗時，請求宣稱的 Client 身分只能標為未驗證，不能記成已驗證呼叫者。安全稽核與必要業務去重紀錄分開管理。

### 憑證與簽章金鑰的登錄核准

信任名單（Client 的用戶端憑證與請求簽章金鑰）只能由已驗證的管理員改變。呼叫服務不能自行把憑證或金鑰加入信任名單，也不能自行核准自己的申請。

登錄流程分為申請與核准兩段：

- Client 提交申請，內容包含 Client 身分、公開憑證或公鑰，以及申請的權限範圍。申請只含公開部分，不得含私鑰。申請者必須通過下述的申請者驗證，不接受匿名申請。
- 申請狀態至少區分待核准、已核准、已拒絕。待核准與已拒絕的申請不得用於取得 Token 或通過簽章驗證。
- 管理員核准後才進入信任名單並生效；拒絕時記錄拒絕結果，不改變信任名單。
- 核准時，憑證與簽章金鑰仍分開管理：核准其中一種不代表另一種已核准。
- 申請以 Client 為界限隔離，核准某 Client 的申請不得改變其他 Client 的憑證、金鑰或權限。

申請者驗證：

- 申請端點只接受已登錄且狀態有效的 Client，並以該 Client 現有已核准的憑證經 mTLS 驗證其身分。被撤銷、停用或已退役憑證的 Client 不能申請。
- 申請的對象只能是申請者自己，不能替其他 Client 提出申請；申請內容宣稱的 Client 必須與已驗證的身分一致，不一致一律拒絕。
- 申請者必須證明持有所申請的新憑證或簽章金鑰的私鑰：憑證申請以該新憑證完成持有證明，簽章金鑰申請以該金鑰對申請內容簽章。證明失敗的申請不建立待核准紀錄。
- 持有證明的簽署內容綁定：已驗證的申請者 Client、申請者目前憑證指紋、所申請新憑證或金鑰的指紋、時間戳、一次性 nonce（lab 暫定表示方式，待使用者確認）。伺服器以自己的時鐘驗證時間窗（持有證明時間窗 60 秒，lab 暫定，待使用者確認），nonce 只能使用一次：同一份證明重送被拒絕，且不新增待核准紀錄、不佔額度。證明內容與申請者身分不符（例如綁定其他 Client 的憑證指紋）一律拒絕。上述拒絕沿用 400 possession_proof_invalid，被拒絕的嘗試仍寫入稽核。
- 每個 Client 的待核准申請數有上限，超過上限的新申請被明確拒絕，不影響既有待核准申請。上限與逾期處理為 lab 暫定值，標註「待使用者確認」。
- 逾期處理（lab 暫定 24 小時，待使用者確認）：待核准申請自提出起 24 小時逾期，到達即視為已過期。逾期的申請不能再被核准或拒絕（409，`request_expired`），不再佔用上限，Client 可再提出申請；管理員查詢回 `expired`。逾期規則為 lab 暫定值，正式採用前須確認。
- 待核准申請紀錄帶有已驗證的申請者身分，供管理員核准時核對。
- 全新 Client 的首次登錄（尚無任何已核准憑證）不屬於本申請端點；其信任來源仍是管理員建立，不在本需求內。
- 失敗回應不得洩漏其他 Client 的申請內容，也不得讓未驗證者區分「Client 不存在」與「身分驗證失敗」。

退役與撤銷同樣只能由已驗證的管理員執行，沿用既有的 60 秒撤銷上限與輪替重疊規則；管理操作本身不得放寬這些限制。

管理員身分：

- 管理員使用專屬的用戶端憑證，經 mTLS 向授權伺服器的管理介面驗證；此憑證登錄為管理角色。
- 管理員身分與 Client 身分分開。管理憑證不能用來取得業務 Token，也不能呼叫業務 API；Client 憑證不能呼叫管理介面。
- 管理介面與業務 API 的驗證結果各自獨立，不共用已驗證呼叫者的判斷。

管理操作稽核：

- 登錄申請、核准、拒絕、退役、撤銷每一次都記錄操作的管理員、時間、對象 Client、憑證或金鑰的指紋與結果。
- 稽核紀錄寫入失敗時，該管理操作不生效，並明確回報服務錯誤。
- 管理操作稽核與既有的呼叫者安全稽核分開管理，且同樣不記錄私鑰、原始 Token。

### 狀態儲存與跨執行個體一致性

目標是讓多個執行個體共用同一組持久儲存時，防重放、業務冪等、信任名單與撤銷仍然成立；先前這些只在單一程序內成立，屬已知限制，此節取代該限制。

**儲存分工**：

| 儲存 | 擁有者 | 內容 |
|---|---|---|
| 授權伺服器資料庫（PostgreSQL） | 授權伺服器 | OpenIddict 的 Client、Authorization、Token；信任名單（憑證、簽章金鑰與其核准／退役／撤銷狀態、Client 啟用狀態）；登錄申請；持有證明 nonce；管理操作稽核 |
| 業務 API 資料庫（PostgreSQL） | 業務 API | 訂單；冪等紀錄與處理中租約；業務唯一鍵；已驗證呼叫者稽核 |
| Redis | 業務 API | 請求簽章 nonce 與防重放紀元 |
| 程序內快取 | 各服務 | 查證快取（Token 查證結果）與信任資料快取，維持程序內，不跨程序共用 |

- 授權伺服器與業務 API 各自擁有獨立資料庫，各只持有自己資料庫的帳號，不能存取對方的資料庫。
- 業務 API 不直接讀授權伺服器資料庫，信任資料一律經授權伺服器取得。
- 持有證明 nonce 與請求簽章 nonce 語意與保存期不同，分開儲存，不合併。

**防重放與防重放紀元**：

- nonce 的「首次登錄」必須是原子操作，併發重放只能有一個成功。
- nonce 保存期涵蓋簽章接受期限加時鐘容差，到期自動清除。
- Redis 紀錄遺失（重啟、被清空）時，防重放紀元重設為當下；簽章建立時間早於紀元的請求一律拒絕，因為它們的 nonce 可能已在遺失前被使用。拒絕後客戶端以新 nonce 與新時間重簽即可。
- 防重放儲存無法使用時 Fail Closed，回報暫時無法驗證，不執行業務副作用。
- nonce 登錄之後，若後續業務提交失敗，不回收 nonce；合法重試本來就必須重簽換新 nonce。
- Redis 是否啟用持久化（AOF）屬未定營運設定；紀元是遺失時的補強，不取代該決定。

**信任資料的取得與快取**：

- 授權伺服器提供內部唯讀的信任資料介面，回傳某 Client 的啟用狀態、有效憑證指紋與有效簽章公開金鑰；業務 API 以既有的 mTLS 服務身分呼叫，取代原本與授權伺服器共用的記憶體物件。
- 業務 API 將結果放程序內快取，快取 TTL 為 10 秒（lab 暫定，待使用者確認），與查證快取同值。
- 無法取得信任資料且沒有仍有效的快取時 Fail Closed，回應 503 `verification_unavailable`。

**撤銷時效的新界線**（60 秒上限不變）：

| 撤銷對象 | 最慢生效時間 |
|---|---|
| Token | 查證快取 TTL（約 10 秒） |
| Client 停用、憑證、簽章金鑰 | 信任資料快取 TTL（約 10 秒）；原本因共用記憶體而立即生效，此為規格變動 |
| 兩層快取最壞相加 | 約 20 秒，仍在 60 秒上限內 |

**授權伺服器的併發與一致性**：

- 管理操作的變更與 `accepted` 稽核放在同一個資料庫交易內，兩者同時成立或同時不成立；OpenIddict 的 Client 登錄與信任名單共用同一個資料庫與交易範圍。
- 套用失敗時整筆交易回滾，另外獨立寫一筆 `failed` 稽核；若這筆也寫不進去，回報稽核無法寫入。此決策取代原本「先寫稽核、再套用，套用例外時稽核已記 `accepted`」的已知缺口。
- 核准與拒絕同一筆申請時，以對該申請資料列的鎖保證只有一個決定生效。
- 每個 Client 的待核准上限，以每個 Client 一把交易內序列化的鎖，讓「計數再新增」不被併發繞過。
- 持有證明 nonce 以唯一約束保證只使用一次，且與建立申請放在同一個交易。

**業務 API 的冪等與稽核**：

- 以 (Client, 業務識別) 與 (Client, Idempotency Key) 的唯一約束保證本地提交不重複；內容比對規則不變。
- 處理中租約為 30 秒，是一筆有到期時間的紀錄；租約逾期後，任一執行個體可用條件式更新接手，租約未逾期前不得接手。隔離等級使用預設的 Read Committed，不使用 Serializable。
- 租約與逾期判斷使用應用程式時鐘，依賴各機器時間同步；時鐘偏差遠小於租約長度，測試以注入時鐘控制。
- 已驗證呼叫者稽核先獨立提交，業務提交失敗時稽核仍保留並記錄結果；這與管理操作不同，管理操作的稽核綁定變更是否成功。

**設定與資料庫結構**：

- 連線資訊走設定與環境變數，不寫進程式碼。
- 資料庫結構的遷移進入版本控制，各資料庫各自一組；只有明確開啟設定時（Lab 與測試）才在啟動時套用，其他環境手動執行。

**與既有決策的關係**：

- 取代 ADR 0001 中關於「程序內儲存」「申請、信任名單與稽核無持久化」「管理操作先寫稽核再套用」「防重放僅程序內」的例外與已知缺口；以新增 ADR 記錄 PostgreSQL 與 Redis 的分工、防重放紀元、兩個資料庫、稽核與變更同交易，以及撤銷時效的規格變動，並在 ADR 0001 對應條目標註已被取代，不刪除原文。
- 考慮過但未採用：只用 PostgreSQL 處理 nonce（避免 Redis 遺失 nonce 的空隙，但每個簽章請求多一次寫入）；兩服務共用同一資料庫與分 schema（保留即時撤銷，但失去資料庫層級隔離）；信任名單改以事件同步副本（一致性成本高於此規模的需要）；查證快取改放 Redis（熱路徑多一個依賴，無規格收益）。

## Testing Decisions

好的測試驗證外部可觀察行為：請求是否被接受、錯誤是否明確、資料是否隔離、業務副作用是否只提交一次，以及撤銷是否符合 60 秒上限。不綁定內部類別、函式呼叫順序或資料表實作。

目前工作目錄只有規格文件，沒有可沿用的程式碼、測試、領域詞彙表或 ADR；未對整個 repository 宣稱不存在相關先例。

建議建立一個主要整合測試邊界：從呼叫端經可信 Gateway 到業務 API 的外部行為。測試環境可控制授權與撤銷狀態、查證服務故障、併發及重試，並觀察本地業務提交與追查結果。涵蓋授權伺服器介接、Gateway 驗證、API 授權／驗簽／防重放，以及本地業務去重能力。

使用者已確認此主要整合測試邊界；目前尚未建立此測試能力。

登錄核准採同一個主要整合測試邊界，不新增第二個測試介面：在授權伺服器上新增管理端點，測試以管理員身分（專屬 mTLS 憑證）經 HTTP 呼叫它，再從呼叫端驗證 Client 的呼叫結果。測試不直接呼叫授權伺服器內部的登錄方法或信任登錄物件。申請者驗證同樣經 HTTP 在此邊界測試，不新增測試介面。不為各內部模組另設多套測試介面。採真實協定與密碼驗證路徑，不以永遠驗證成功的替身證明 mTLS 或簽章保證。

狀態儲存與跨執行個體保證沿用同一個測試縫，不新增縫：

- 縫仍是真實 mTLS 上的 HTTP 邊界；縫後面的儲存換成真實的 PostgreSQL（授權伺服器與業務 API 各一個資料庫）與 Redis，由容器提供，不用記憶體提供者或假實作，因為唯一約束、交易與原子登錄的行為只有真實服務才能證明。
- 跨執行個體以在同一測試程序內啟動每個服務的兩個執行個體、共用同一組資料庫與 Redis 來驗證，不依賴同程序共用物件。
- 故障情境（儲存不可用、稽核寫入失敗、信任資料端點不可用）以對真實服務製造故障取得，取代原本以旗標跳過儲存的模擬。
- 防重放紀錄遺失以清空 Redis 這個基礎設施動作製造；租約逾期與待核准逾期以注入時鐘控制，不真的等待。
- 測試只觀察外部行為，不直接讀寫資料表；資料庫帳號隔離（AC-43）以各服務自己的帳號嘗試跨庫存取驗證。
- 先例：現有 Reqnroll Feature、真實 Kestrel TLS 啟動方式與各服務啟動輔助都沿用，只替換儲存與增加執行個體數。

### 驗收情境

以下是未來實作的驗收要求，不代表目前已通過：

| 編號 | 情境 | 預期結果 |
|---|---|---|
| AC-01 | 無有效用戶端憑證請求 Token | 不核發 Token |
| AC-02 | 只持有被偷的 Token，沒有綁定憑證的私鑰 | 無法通過 API 接受判斷 |
| AC-03 | 混用不同 Client 的合法 Token、憑證或簽章 | 拒絕 |
| AC-04 | 撤銷 Token、Client、憑證或簽章金鑰 | 各驗證端含既有連線上的後續請求，最多 60 秒內阻擋 |
| AC-05 | 查證服務故障，沒有符合時效的有效快取 | 拒絕處理，明確回報服務錯誤，無業務副作用 |
| AC-06 | 偽造 Gateway 身分標頭或繞過 Gateway | 不被接受為可信呼叫 |
| AC-07 | 改動已簽署目標、必要標頭或 Body | 簽章／摘要驗證失敗 |
| AC-08 | 同一份簽章向多個執行個體併發重放 | 不重複通過 nonce 接受判斷 |
| AC-09 | 合法重簽重試或併發提交同一業務操作 | 本地副作用只提交一次，回傳既有結果或處理狀態 |
| AC-10 | 相同識別但不同業務內容 | 拒絕，不覆寫 |
| AC-11 | 提交完成但回應遺失，或短期去重紀錄已過期 | 重試不重做同一筆業務副作用 |
| AC-12 | 有 scope，但要求其他廠商／租戶的資料 | 資料範圍授權拒絕 |
| AC-13 | 正常輪替後，拿舊 Token 搭配新憑證 | 拒絕；新憑證取得自己的 Token 後可正常使用 |
| AC-14 | 檢查追查紀錄 | 可辨識已驗證呼叫者，無原始 Token、私鑰或完整敏感 Body |
| AC-15 | 未經管理員驗證（無管理憑證，或持 Client 憑證）呼叫管理介面 | 拒絕，信任名單不變 |
| AC-16 | 提交登錄申請但管理員尚未核准 | 申請中的憑證或金鑰不能取得 Token，也不能通過簽章驗證 |
| AC-17 | 管理員核准申請 | 該憑證或金鑰生效，Client 可取得綁定該憑證的 Token；核准其中一種不使另一種生效 |
| AC-18 | 管理員拒絕申請 | 不生效，並記錄拒絕結果 |
| AC-19 | 管理員退役或撤銷憑證或金鑰 | 依既有輪替與 60 秒撤銷規則生效；非管理員不能執行 |
| AC-20 | 管理憑證用來取得業務 Token 或呼叫業務 API | 拒絕 |
| AC-21 | 檢查管理操作稽核 | 可辨識操作的管理員、時間、對象 Client、指紋與結果，無私鑰或原始 Token |
| AC-22 | 管理操作稽核寫入失敗 | 該管理操作不生效，明確回報服務錯誤 |
| AC-23 | 核准某 Client 的申請 | 其他 Client 的憑證、金鑰與權限不變 |
| AC-24 | 未經驗證（無憑證或未登錄憑證）送出登錄申請 | 拒絕，不建立待核准紀錄 |
| AC-25 | Client A 以自己的身分替 Client B 提出申請 | 拒絕，B 的待核准清單不變 |
| AC-26 | 申請新憑證或金鑰，但無法證明持有對應私鑰 | 拒絕，不建立待核准紀錄 |
| AC-27 | 已登錄 Client 以現有憑證為自己申請並證明持有新私鑰 | 建立待核准紀錄，帶已驗證的申請者身分 |
| AC-28 | 同一 Client 的待核准申請超過上限 | 新申請被明確拒絕，既有待核准申請不受影響 |
| AC-29 | 被撤銷、停用或已退役憑證的 Client 提出申請 | 拒絕 |
| AC-30 | 被拒絕的申請嘗試（未驗證、證明失敗、超過上限） | 留下標為未驗證的紀錄；操作者狀態維持「未驗證」，不把宣稱的 Client 記成已驗證；另以獨立的申請者驗證欄位記錄 mTLS 申請者是否通過驗證及通過時的申請者 Client（匿名者為未通過且不含任何宣稱身分，lab 暫定、待使用者確認）；失敗回應不洩漏他人申請內容 |
| AC-31 | 同一份簽章併發送往兩個業務 API 執行個體 | 只有一個通過防重放，另一個被拒絕且無業務副作用 |
| AC-32 | 防重放紀錄遺失（重啟或被清空）後，重放遺失前建立的簽章 | 因簽章建立時間早於防重放紀元而被拒絕，無業務副作用；紀元之後建立的簽章照常通過 |
| AC-33 | 防重放儲存無法使用 | 拒絕處理並明確回報服務錯誤（Fail Closed），無業務副作用 |
| AC-34 | 兩個業務 API 執行個體併發提交同一業務操作（相同 Idempotency Key 或相同業務識別） | 本地副作用只提交一次；另一個回既有結果或處理中；內容不同者拒絕且不覆寫 |
| AC-35 | 處理中的租約逾期後，由另一個執行個體重試同一業務操作 | 可接手且不產生重複副作用；租約未逾期前不得接手 |
| AC-36 | 管理操作套用失敗 | 信任名單與 `accepted` 稽核都不留下；留下一筆 `failed` 稽核；若 `failed` 稽核也寫不進去，回報服務錯誤 |
| AC-37 | 兩位管理員或兩個授權伺服器執行個體同時核准、拒絕同一筆申請 | 只有一個決定生效，另一個得到「申請非待核准」的明確回應 |
| AC-38 | 同一 Client 併發提交申請 | 待核准總數不超過上限 |
| AC-39 | 同一份持有證明併發送出兩次 | 只建立一筆待核准申請，另一次被拒絕且不佔用額度 |
| AC-40 | 授權伺服器重啟或由另一個執行個體接手 | 信任名單、登錄申請、稽核與已核發的 Token 仍然有效且一致 |
| AC-41 | 撤銷 Client、憑證或簽章金鑰後，各業務 API 執行個體收到請求 | 最慢一個信任資料快取 TTL（lab 暫定 10 秒）後全部阻擋，且不超過 60 秒上限 |
| AC-42 | 業務 API 無法取得信任資料且沒有仍有效的快取 | 拒絕處理並回報暫時無法驗證（503），無業務副作用 |
| AC-43 | 業務 API 以自己的資料庫帳號存取授權伺服器資料庫，或反向存取 | 拒絕存取；兩個服務各自只能存取自己的資料庫 |

## Out of Scope

- 代表使用者存取資源、互動式登入與其他 OAuth grant 選型。
- 容量規劃與部署；授權伺服器、簽章、狀態儲存的選型已確定，其餘產品（例如 Gateway）仍待決定。
- 跨服務或外部系統的 exactly-once 保證；另訂下游冪等協定。
- 以 API Key 或 Client Secret 作為額外認證方案。
- Token 與對應私鑰同時外洩時的完整防冒用保證。
- 以請求簽章取代 TLS 或提供資料加密。
- 全新 Client 的首次登錄與首次憑證的傳遞管道（工單、人工轉交或自助入口）；本規格只定義已登錄 Client 的申請者驗證，以及申請提交後的狀態與核准規則。
- 多人覆核（four-eyes）、管理員角色細分與管理員本身憑證的頒發流程。
- 憑證由 CA 簽發的信任鏈與頒發（本專案採自簽憑證，信任來自管理員核准登錄）。
- PostgreSQL 與 Redis 的高可用、叢集、備份還原與災難復原；本規格只定義單一資料庫與單一 Redis 實例下的行為保證。
- 查證快取與信任資料快取的跨程序共用；兩者維持程序內快取。
- 全新 Client 首次登錄所需的資料庫帳號與連線憑證頒發，以及資料庫帳號輪替流程。
- 既有資料遷移：本專案目前只有程序內暫存資料，沒有需要搬遷的正式資料。

- 正常輪替重疊期、稽核保存期及營運流程。
- 各 API 的最長重試期與下游冪等協定。
- 管理介面的路徑與回應格式、申請內容欄位、申請與核准的 HTTP 狀態／錯誤格式。

- 已驗證呼叫者稽核的保存期與存取規則。

### 保證限制與參考

Token 與對應私鑰一起外洩，不在「Token 被偷後不能單獨使用」的保證內。請求簽章不取代 TLS，也不提供資料加密。上述組合是本次六項目標的選型，不是所有 server-to-server API 的最低配置。

- [OAuth 2.0 Client Credentials：RFC 6749 §4.4](https://www.rfc-editor.org/rfc/rfc6749.html#section-4.4)
- [Token Introspection：RFC 7662](https://www.rfc-editor.org/rfc/rfc7662.html)
- [mTLS 用戶端認證與憑證綁定 Token：RFC 8705](https://datatracker.ietf.org/doc/html/rfc8705)
- [HTTP Message Signatures：RFC 9421](https://datatracker.ietf.org/doc/html/rfc9421)
- [HTTP 內容摘要：RFC 9530](https://datatracker.ietf.org/doc/html/rfc9530)
